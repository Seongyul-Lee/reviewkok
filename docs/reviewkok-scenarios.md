# 리뷰콕 대표 시나리오

> `reviewkok-idea.md` 7절의 시나리오를 구조 설계에 쓸 수 있게 풀어 쓴 문서.
> 아직 정하지 않은 부분은 임의로 채우지 않고 **[결정 필요 Dn]** 으로 표시했다. 목록은 문서 끝에 있다.

## 공통 설정

- 행위자: 대학가에서 홀 영업 위주의 치킨집을 하는 사장 김씨 (1개 매장, 베이직 요금제)
- 연결된 채널: 네이버 플레이스 (공식 제휴 연동) **[D1]**
- 답글 말투: 정중함
- 알림: 카카오 알림톡 수신 동의 완료

## 시나리오 1. 영업 중 긴급 리뷰 대응

금요일 저녁, 주문이 몰려 김씨는 휴대폰을 볼 틈이 없다. 놓치면 안 되는 리뷰 하나만 알림으로 받아 처리한다.

### 기본 흐름

| 시각 | 사용자 | 시스템 | 외부 시스템 |
|---|---|---|---|
| 19:10 | | | 고객이 네이버 지도에 "치킨에서 머리카락이 나왔어요" 리뷰 작성 |
| 19:12 | | 새 리뷰 3건을 가져오고, 이미 가져온 리뷰는 걸러낸다 **[D1]** | 네이버 플레이스 제휴 API |
| 19:12 | | 3건을 Jev로 판정한다: 감정, 불만 유형, 긴급도, 답글 필요 여부, 각 신뢰도 | Jev API |
| 19:12 | | 판정 결과로 리뷰를 나눈다: **긴급** / **확인 필요** / **일반** **[D2: 나누는 기준]** | |
| 19:12 | | 머리카락 리뷰는 위생, 긴급도 0.94, 신뢰도 높음, 답글 필요 → **긴급** | |
| 19:12 | | 긴급 리뷰의 답글 초안을 정중한 말투로 만든다 **[D3: 알림과 초안의 순서]** | LLM API |
| 19:13 | | 김씨에게 알림톡을 보낸다 (리뷰 요약 + 상세 화면 링크) | 카카오 알림톡 |
| 19:15 | 알림을 연다 | 리뷰 원문, 판정 결과, 답글 초안을 보여 준다 **[D4: 앱인가 모바일 웹인가]** | |
| 19:16 | 초안을 조금 고치고 게시한다 | 답글을 게시한다 **[D5: 게시 방식]** | 네이버 플레이스 제휴 API |
| 19:16 | | 리뷰 상태를 "답글 완료"로 바꾼다 | |
| — | | 나머지 2건은 피드에 쌓아 두고 알림을 보내지 않는다 | |

### 예외 흐름

- **E1. Jev 호출이 실패하거나 느리다** → 재시도한다. 그래도 실패한 리뷰를 어떻게 다룰지 정해야 한다. 미분류로 두면 긴급 리뷰를 놓칠 수 있다. **[D6]**
- **E2. 긴급도는 높은데 신뢰도가 낮다** → 알림을 보낼지, "확인 필요" 목록에만 넣을지 정해야 한다. 차별점 (a) "놓치면 안 되는 리뷰를 먼저 잡는다"와 (c) "신뢰도가 낮으면 사람이 본다"가 여기서 부딪친다. **[D2]**
- **E3. 초안 생성이 실패한다** → 알림은 그대로 보내고, 상세 화면에서 "초안 다시 만들기"를 제공한다.
- **E4. 알림톡 발송이 실패한다** → 다른 수단으로 대신 보낼지 정해야 한다. **[D7]**

## 시나리오 2. 마감 후 리뷰 정리와 주간 리포트

마감 후 김씨가 남은 리뷰를 한 번에 정리한다. 이렇게 사람이 확정한 판정이 쌓여 월요일 리포트의 재료가 된다.

### 기본 흐름

| 시각 | 사용자 | 시스템 | 외부 시스템 |
|---|---|---|---|
| 23:30 | 앱을 연다 | 피드를 보여 준다: 확인 필요 1건, 답글 안 단 리뷰 13건 (긍정 11, 경미한 불만 2), 처리한 긴급 리뷰 1건 | |
| 23:31 | 확인 필요 리뷰를 연다: "좀 짰는데 맥주랑 먹으니 딱이네요 ㅋㅋ" | AI 판정 후보와 함께 "AI가 확신하지 못한 리뷰"라고 표시한다 | |
| 23:31 | 감정은 긍정, 불만 유형은 맛(경미), 답글 필요는 예로 확정한다 | 사람이 확정한 판정을 AI 판정과 **함께** 저장한다 (나중에 정확도를 재는 데이터) | |
| 23:32 | | 이 리뷰의 답글 초안을 만든다 | LLM API |
| 23:33 | 경미한 불만 2건과 방금 리뷰의 초안을 고쳐 게시한다 | 답글을 게시하고 상태를 바꾼다 **[D5]** | 네이버 플레이스 제휴 API |
| 23:36 | 긍정 리뷰 11건을 훑어본다 | 답글이 필요하다고 판정된 리뷰에만 초안이 있다 **[D8: 긍정 리뷰의 답글 기준]** | |
| 월 09:00 | | 지난주 판정(사람이 확정한 것은 그 값)을 불만 유형별로 모아 주간 리포트를 만든다 | 스케줄러 |
| 월 09:00 | | 리포트 준비 알림을 보낸다 | 카카오 알림톡 |
| 월 09:20 | 리포트를 연다: "대기 시간 불만 3주 연속 증가" | 유형별 건수 추이, 나아진 항목과 나빠진 항목을 보여 준다 | |

### 예외 흐름

- **E5. 김씨가 확인 필요가 아닌 리뷰의 판정을 고친다** → 확인 필요 리뷰와 똑같이 사람 판정으로 저장하고, 리포트에는 고친 값을 쓴다.
- **E6. 게시가 실패한다** (플랫폼 오류, 리뷰 삭제, 답글 기간 만료) → 초안을 잃지 않게 남겨 두고 실패 이유를 보여 준다.
- **E7. 지난주 리뷰가 너무 적다** → 추이를 말하기 어려우니 "데이터 부족"으로 표시한다. 최소 건수를 정해야 한다. **[D9]**

## 결정 필요 목록

각 항목의 결정은 `reviewkok-architecture.md` 2절에 있다.

| ID | 질문 | 영향 |
|---|---|---|
| D1 | 리뷰를 어떻게 가져오는가 (공식 API / 사장님 계정 연동 / 직접 업로드), 얼마나 자주 가져오는가 | 수집 어댑터와 스케줄러 구성, 법적 리스크, "실시간"이 가능한지 |
| D2 | 긴급 / 확인 필요 / 일반을 나누는 기준. 특히 긴급도는 높고 신뢰도는 낮은 경우 | 핵심 도메인 규칙. 차별점 (a)와 (c)의 우선순위 |
| D3 | 알림을 초안 생성 뒤에 보내는가, 먼저 보내는가 | 알림이 늦어질 수 있는지, 처리 흐름을 동기로 할지 비동기로 할지 |
| D4 | 사장님 화면을 앱으로 만드는가, 모바일 웹으로 만드는가 | Frameworks 계층의 UI 기술, 알림 링크 방식 |
| D5 | 답글을 리뷰콕에서 바로 게시하는가, 초안을 복사해 플랫폼에서 직접 게시하는가 | 게시 어댑터가 있는지, "답글 완료"를 어떻게 확인하는지 |
| D6 | Jev가 실패한 리뷰를 어떻게 다루는가 (키워드 규칙으로 대신 판정 / 다른 모델 / 확인 필요로 보냄) | 분류 모듈 교체 구조의 범위 |
| D7 | 알림톡이 실패하면 다른 수단으로 보내는가 | 알림 어댑터 수 |
| D8 | 긍정 리뷰에도 답글 초안을 만드는가 | LLM 호출 수, 즉 원가와 저가 요금제(차별점 b) |
| D9 | 주간 리포트에서 추이를 말하려면 최소 몇 건이 필요한가 | 리포트 규칙 |

## 시나리오에서 나온 유스케이스 후보

다음 단계(계층 다이어그램)의 재료다.

- 리뷰 수집하기
- 리뷰 판정하기 (Jev)
- 판정 결과로 리뷰 나누기 (긴급 / 확인 필요 / 일반)
- 답글 초안 만들기 (LLM)
- 긴급 알림 보내기
- 답글 게시하기
- 사람이 판정 확정하기
- 주간 리포트 만들기

외부 시스템(Frameworks 계층 후보): 네이버 플레이스 제휴 API(이후 배달앱 등 제휴 채널), Jev API, LLM API, 카카오 알림톡, 스케줄러, DB, 사장님 화면(앱 또는 웹)
